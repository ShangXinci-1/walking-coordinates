# 《行走的坐标》前端重构实施计划

> 文档版本：V1.0
> 编制日期：2026-07-27
> 依据文档：《行走的坐标》前端完整改版方案 V1.2
> 文档性质：实施顺序、工程决策、数据取证规则与验收门禁
> 适用分支：`codex/frontend-redesign`

## 1. 实施目标与边界

### 1.1 实施目标

#### 1.1.1 目标状态

在保留 Next.js 静态导出、GitHub Pages 部署和 `/walking-coordinates` 基础路径的前提下，将现有展示原型重构为由集中数据、来源记录、内容状态和可替换素材驱动的生产级公开网站。

#### 1.1.2 核心结果

重构完成后，四个公开页面应当共同使用统一的设计 Token、导航、状态、路线、地点、成果和素材数据；用户能够在桌面端、移动端和键盘环境中完成设计方案规定的主要浏览流程。

#### 1.1.3 可信度要求

项目不得把 Agent 推断、搜索摘要、未确认坐标、示意影像或规划中的成果写成已核验事实。所有地点、历史说明、实践动作、坐标、媒体和成果状态都必须能够追溯到明确来源或项目团队确认记录。

### 1.2 本次重构范围

#### 1.2.1 页面范围

- 首页 `/`
- 寻访路线 `/journey`
- 数字成果 `/outcomes`
- 精神传承 `/legacy`

#### 1.2.2 工程范围

- 全局设计 Token、栅格、字体和交互状态
- 公共页头、移动菜单、页脚和页面元数据
- 路线、地点、来源、成果和素材的数据模型
- 首页叙事结构
- 路线索引、坐标关系图和地点档案
- 成果状态、图库灯箱和传承内容
- 静态图片交付、URL 状态恢复、无障碍和自动化验证

#### 1.2.3 非本轮范围

- 后端服务、账号系统和内容管理后台
- 在线编辑和多人协作
- 导航、路径规划或实时定位
- 未取得授权的第三方地图瓦片、摄影、视频或文字内容
- 将筹备中的成果包装成已完成成果

### 1.3 当前代码基线

#### 1.3.1 可保留部分

- Next.js App Router 与静态导出配置
- 四个一级路由
- 现有品牌红、深红、黑、白色彩基础
- `SiteHeader`、`SiteFooter`、`RouteMap` 和灯箱的交互雏形
- `prefers-reduced-motion` 基础规则

#### 1.3.2 需要重构部分

- 页面内重复硬编码的路线、地点、成果与图库数据
- `globals.css` 与 `custom.css` 的重复覆盖关系
- 当前不具备地理或档案语义的 SVG 地图
- 缺少焦点管理和键盘语义的地图节点与灯箱
- 未被页面引用的 `PracticeSite.tsx`
- 仅显示“现场照片 1—5”的无身份占位素材

## 2. 已核定的工程与数据决策

### 2.1 决策 D-001：路线可视化不直接接入在线地图

#### 2.1.1 核定结果

第一版正式实现采用“路线坐标关系图”，不接入高德、百度、腾讯、天地图、OpenStreetMap 或其他在线地图底图，不绘制北京市行政区边界，也不提供导航能力。

坐标关系图只表达路线顺序、地点归属和章节切换。地点的真实经纬度作为档案字段独立展示，不使用未经审核的行政区轮廓暗示地理精度。

#### 2.1.2 核定理由

1. 公开地图和附着地图图形产品受地图管理与内容表示规范约束。
2. 高德 JS API 的生产安全模式需要代理服务器携带安全密钥转发；当前项目是纯静态 GitHub Pages，无法安全承担这一代理职责。
3. 在线地图会增加外部脚本、密钥、网络可用性、性能、无障碍和隐私依赖，与本项目“静态、可信、可长期保存”的目标不匹配。
4. 当前核心任务是解释实践路线与地点档案，而不是提供地理导航。

#### 2.1.3 视觉约束

- 组件名称使用 `RouteDiagram`，不使用 `BeijingMap`。
- 页面文案使用“路线坐标关系图”或“路线示意”，不使用“精确地图”。
- 图形不出现北京市行政边界、道路、比例尺或导航指示。
- 节点布局依据路线章节和阅读顺序，不宣称节点间视觉距离代表实际距离。
- 每个地点档案单独显示经纬度、坐标系、定位对象和来源状态。

#### 2.1.4 后续升级门槛

只有在项目方同时提供以下条件后，才评估接入真实地图：

1. 明确选择持证地图服务商；
2. 明确 API Key、域名白名单和生产代理的责任人；
3. 明确地图内容审核与合规责任人；
4. 完成外部服务不可用时的降级方案；
5. 完成键盘、屏幕阅读器和减少动态效果验证。

### 2.2 决策 D-002：经纬度采用 GCJ-02 并保留来源

#### 2.2.1 核定结果

地点坐标的项目内标准为 GCJ-02。每个坐标必须同时记录坐标系、定位对象、精度类型、数据来源、核验日期和核验人。

#### 2.2.2 数据结构

```ts
interface CoordinateRecord {
  lat: number;
  lng: number;
  crs: "GCJ-02";
  target: "main-entrance" | "site-center";
  precision: "verified-poi" | "manual-pin";
  sourceId: SourceRecord["id"];
  verifiedAt: string;
  verifiedBy: string;
}
```

#### 2.2.3 选择理由

- 高德地理编码直接返回高德经纬度，避免在项目中执行来源不明的坐标转换。
- GCJ-02 便于项目方在国内地图服务中人工复核。
- 明确坐标系可避免把 WGS84、GCJ-02 和 BD-09 数据混合使用。

#### 2.2.4 禁止事项

- 不根据建筑名称让 Agent 直接生成经纬度。
- 不复制搜索结果摘要中的坐标。
- 不将不同坐标系的数据直接放入同一数组。
- 不使用未注明入口、中心点或定位对象的“高精度”数字。
- 不在没有来源记录时把坐标状态设为 `verified`。

### 2.3 决策 D-003：坐标采集采用候选生成与人工晋级流程

#### 2.3.1 输入

每个地点首先从场馆官网、北京市政府、北京市文物局或其他主管单位取得正式名称和结构化地址。

#### 2.3.2 候选生成

由项目方持有的高德 Web 服务 Key 调用地理编码接口。Key 只通过本地环境变量传入，不写入仓库。脚本输出候选文件，不直接修改正式地点数据。

建议命令：

```powershell
$env:WC_AMAP_WEB_KEY="<由项目方提供>"
npm run data:geocode
```

候选输出路径：

```text
data/generated/geocode-candidates.json
```

#### 2.3.3 人工复核

复核者必须同时检查：

1. 返回 POI 名称是否与正式地点一致；
2. 地址是否与主管单位页面一致；
3. 点位对应主入口还是场地中心；
4. 地点是否存在同名对象；
5. 坐标系是否为 GCJ-02。

#### 2.3.4 正式晋级

人工复核后，将坐标和来源信息写入正式 `SiteRecord`，并填写 `verifiedAt` 与 `verifiedBy`。自动脚本不得自行完成此步骤。

### 2.4 决策 D-004：事实内容使用来源分级制度

#### 2.4.1 来源等级

| 等级 | 来源 | 可承担用途 |
|---|---|---|
| A | 场馆官网、中央或地方政府、文物主管部门、项目团队原始记录 | 正式名称、地址、历史摘要、开放状态、实践事实 |
| B | 正式出版物、学术机构、权威数据库 | 历史补充、交叉验证 |
| C | 新闻报道、地图 POI、可信媒体 | 线索发现、地址或状态辅助核验 |
| D | 聚合页、社交媒体、搜索摘要、AI 输出 | 仅作搜索线索，不进入正式内容 |

#### 2.4.2 事实字段要求

- `name`：至少一个 A 级来源。
- `officialAddress`：至少一个 A 级来源。
- `historySummary`：至少一个 A 级来源；涉及具体年份、人物或事件时增加第二来源。
- `practiceSummary`：必须来自项目团队原始记录，不能由公开网页推断。
- `coordinate`：A 级正式地址加指定地理编码结果，并完成人工复核。
- `sourceNotes`：显示用户可理解的来源名称，不只保存 URL。
- `contentStatus`：由内容负责人确认，不由 Agent 根据页面完整程度自行判断。

#### 2.4.3 来源记录结构

```ts
interface SourceRecord {
  id: string;
  title: string;
  publisher: string;
  url: string;
  level: "A" | "B" | "C";
  sourceType:
    | "official-venue"
    | "government"
    | "project-record"
    | "publication"
    | "geocoder";
  accessedAt: string;
  supports: string[];
}
```

#### 2.4.4 引用完整性门禁

构建前运行数据校验。任何 `ready` 或 `partial` 地点缺少必需来源时，构建失败；`placeholder` 或 `planned` 内容允许字段为空，但页面必须显示相应状态。

### 2.5 决策 D-005：十三处地点是目标清单，不自动视为实践事实

#### 2.5.1 目标清单

实施以设计方案中的 13 个地点建立数据槽位：

- 觉醒之路：5 处
- 烽火之路：5 处
- 进京之路：3 处

#### 2.5.2 内容状态

在项目团队确认实际寻访记录前，新增地点只能标记为 `planned` 或 `placeholder`。不得仅因地点出现在设计文档中，就写成团队已经实地寻访。

#### 2.5.3 开发前确认项

项目负责人需要确认：

1. 13 个地点是否均属于本次实际实践；
2. 各地点所属路线和先后顺序；
3. 各地点是否存在照片、访谈、全景或资料记录；
4. “14 天”与各路线日期是否与真实行程一致。

### 2.6 决策 D-006：素材由清单驱动，不以文件是否存在推断状态

#### 2.6.1 核定结果

所有图片、视频、VR 和报告通过 `AssetRecord` 引用。页面只读取固定素材 ID，不直接拼接临时路径。

#### 2.6.2 占位素材

占位素材必须包含素材 ID、目标场景、宽高比、拍摄要求和“示意素材”标识。占位素材不得模拟真实历史照片，也不得使用无来源网络图片充当实践记录。

#### 2.6.3 正式素材晋级

正式素材只有在文件、授权、alt、署名、拍摄日期和用途全部齐备时，才能切换为 `ready`。

#### 2.6.4 图片交付

- 仓库保存预生成 AVIF 与 WebP。
- 组件使用 `<picture>`、明确宽高和响应式 `srcset`。
- 首屏主图按页面需要预加载。
- 非首屏媒体懒加载。
- 静态部署不依赖运行时图片转换服务。

### 2.7 决策 D-007：查询参数只保存交互状态

#### 2.7.1 URL 结构

```text
/journey?route=awakening&site=beida-honglou
```

#### 2.7.2 实现方式

- `/journey` 保持一个静态导出页面。
- 查询参数由客户端边界读取和更新。
- `useSearchParams` 所在组件放入 `Suspense` 边界，满足静态渲染要求。
- 参数必须与集中数据中的 slug 匹配。
- 无效参数回退到第一条路线和第一个地点，并使用 `replaceState` 修正 URL。
- 用户主动切换路线或地点时使用 `pushState`，保证浏览器前进和后退可恢复状态。

#### 2.7.3 SEO 规则

- 查询参数不产生独立静态页面或独立 canonical。
- `/journey` 是规范页面 URL。
- 分享链接保留参数以恢复交互状态。
- 如果未来需要每个地点独立被搜索引擎索引，再升级为静态动态路由 `/journey/[site]`，不在本轮提前实现。

### 2.8 决策 D-008：无障碍目标高于最低触控要求

#### 2.8.1 核定结果

WCAG 2.2 AA 是发布门槛；主要交互控件继续采用设计方案中的 44×44px 目标尺寸。44px 是项目设计目标，不误写成 WCAG 2.2 AA 的统一法定最小值。

#### 2.8.2 组件约束

- 路线和地点使用真实 `<button>` 或可访问的复合组件，不对纯 SVG `<g>` 直接绑定唯一交互。
- 路线图与地点列表提供等价操作路径。
- 灯箱使用原生 `<dialog>` 或经过验证的 portal 方案。
- 所有焦点状态使用至少 2px 的高对比轮廓。
- 移动菜单、灯箱和复合组件验证焦点进入、循环、退出与恢复。
- 减少动态效果模式不改变内容和操作能力。

### 2.9 决策 D-009：集中数据是唯一事实入口

#### 2.9.1 目标目录

```text
data/
  routes.ts
  sites.ts
  assets.ts
  outcomes.ts
  sources.ts
  generated/
lib/
  content/
    types.ts
    selectors.ts
    validate.ts
scripts/
  geocode-sites.mjs
  validate-content.mjs
```

#### 2.9.2 页面使用规则

- 页面组件不得再次声明路线、地点、素材或成果数组。
- 数量、状态和上下一个地点均由 selector 派生。
- 页面不得硬编码“13 处”“已开放”等可能变化的事实。
- 组件接收明确的视图模型，不自行搜索或补齐数据。

## 3. 数据搜寻与核验工作流

### 3.1 地点事实工作流

#### 3.1.1 建立待核验表

为 13 个地点创建记录，初始状态均为 `draft`，字段包含正式名称、设计名称、路线、顺序、正式地址、坐标、历史摘要、实践摘要和来源。

#### 3.1.2 正式名称核验

优先查询场馆官网、北京市文化和旅游局、北京市文物局或北京市政府页面。记录页面标题、发布机构、URL 和访问日期。

#### 3.1.3 地址与坐标核验

先确定正式地址，再执行第 2.3 节的地理编码候选与人工晋级流程。坐标不能反向决定正式地点身份。

#### 3.1.4 历史摘要核验

摘要先写“事实句清单”，每句绑定来源 ID，再组合成页面段落。无法找到来源的句子保持缺失，不由 Agent 补写。

#### 3.1.5 实践记录核验

实践动作、拍摄日期、采访对象和采集方式只能来自团队日志、照片 EXIF、采访记录或负责人确认。

#### 3.1.6 内容负责人确认

负责人逐地点确认后，将数据状态从 `draft` 升级为 `reviewed`；只有 `reviewed` 数据才能进入 `partial` 或 `ready` 页面状态。

### 3.2 成果状态工作流

#### 3.2.1 成果登记

每项成果记录负责人、实际文件或访问地址、当前完成度、公开权限、发布日期和更新日期。

#### 3.2.2 状态判定

- `planned`：尚无可验证交付物。
- `partial`：存在可验证的阶段性内容，但未达到完整公开标准。
- `ready`：用户点击后可以访问与文案一致的正式内容。

#### 3.2.3 动作一致性

没有真实目标时不显示“进入”“播放”“下载”等动作。筹备中内容只显示状态和交付条件。

### 3.3 素材工作流

#### 3.3.1 入库

素材按设计方案规定的 ID 和目标路径入库，保留原始文件、网页交付文件和授权记录之间的对应关系。

#### 3.3.2 自动检查

脚本检查文件是否存在、尺寸、宽高比、格式、文件大小、必填 alt 和 credit。

#### 3.3.3 人工检查

人工确认画面身份、人物授权、叙事用途、裁切安全区和颜色处理。

#### 3.3.4 发布晋级

自动与人工检查均通过后，更新 `AssetRecord.status`。页面不得根据 `finalSrc` 非空自动推断为 `ready`。

### 3.4 Agent 工作约束

#### 3.4.1 允许

- 从指定来源提取候选事实并保留原始 URL；
- 生成待核验表、校验脚本和缺失项报告；
- 根据已确认数据编写组件与测试；
- 标记来源冲突和无法确认的内容。

#### 3.4.2 不允许

- 以模型记忆补齐地点地址、坐标、历史年份或项目实践事实；
- 用搜索摘要代替原始来源；
- 在来源冲突时自行选取更符合叙事的版本；
- 将文件存在、页面美观或字段非空推断为内容已完成；
- 生成看似真实的历史现场照片作为正式证据。

#### 3.4.3 冲突处理

来源冲突时保留全部候选、记录差异并标记 `needs-review`。在项目负责人确认前，页面使用中性文案或保持字段缺失。

## 4. 目标工程结构

### 4.1 页面与组件

#### 4.1.1 页面层

页面负责元数据、章节顺序和服务端静态结构，不持有重复业务数据。

#### 4.1.2 交互层

客户端组件只用于移动菜单、路线与地点选择、URL 同步和灯箱。

#### 4.1.3 组件建议

```text
components/
  shell/
    SiteHeader.tsx
    MobileMenu.tsx
    SiteFooter.tsx
  evidence/
    EvidenceStrip.tsx
    StatusBadge.tsx
    SourceList.tsx
  media/
    ResponsiveMedia.tsx
    MediaPlaceholder.tsx
    MediaDialog.tsx
  routes/
    RouteIndex.tsx
    RouteDiagram.tsx
    SiteList.tsx
    SiteDossier.tsx
  outcomes/
    OutcomeRecord.tsx
```

### 4.2 样式系统

#### 4.2.1 文件边界

- `app/globals.css`：重置、Token、基础排版、焦点和减少动态效果。
- `styles/layout.css`：全局容器、栅格和响应式结构。
- `styles/components/*.css`：组件样式。
- 页面局部样式使用 CSS Module 或明确页面命名空间。

#### 4.2.2 迁移规则

新组件完成后再删除对应旧选择器。不得先整体删除现有样式，也不得继续依赖 `!important` 叠加覆盖。

#### 4.2.3 Token 规则

颜色、内容宽度、间距、动效、圆角、层级和焦点统一通过 Token 使用。页面组件不得重复声明同义魔法值。

### 4.3 内容校验

#### 4.3.1 类型校验

TypeScript 使用 `satisfies` 保证数据形状，并由纯函数验证跨记录约束。

#### 4.3.2 跨记录约束

- 路线引用的地点必须存在且属于该路线。
- 地点顺序在路线内唯一。
- 素材 ID 全局唯一。
- `ready` 素材文件必须存在。
- `ready` 内容必须拥有规定来源。
- slug 必须稳定、唯一且可安全进入 URL。

## 5. 分阶段实施顺序

### 5.1 阶段零：数据与内容基线

#### 5.1.1 开发任务

1. 建立 `types.ts`、五类集中数据文件和校验器。
2. 将当前硬编码数据迁入集中数据。
3. 建立 13 个地点的状态槽位。
4. 创建来源记录和缺失字段报告。
5. 建立地理编码候选脚本接口，但不提交 Key。

#### 5.1.2 自动化验证

- 数据类型检查
- ID、slug、路线归属和顺序唯一性测试
- 来源与内容状态规则测试
- Key 与生成候选文件不进入 Git 的检查

#### 5.1.3 退出条件

所有页面可从集中数据读取；不存在第二份路线、地点或成果数组；未核验数据明确显示状态。

### 5.2 阶段一：基础系统

#### 5.2.1 开发任务

1. 重建 Token、全局排版、容器和焦点系统。
2. 实现桌面导航、移动菜单和当前栏目。
3. 实现 `StatusBadge`、`EvidenceStrip`、`MediaPlaceholder` 和 `ResponsiveMedia`。
4. 为四页面建立独立元数据。

#### 5.2.2 自动化验证

- TypeScript、ESLint、静态构建
- 导航与移动菜单 Playwright 测试
- axe 基础扫描
- 320px 与 1440px 导航截图

#### 5.2.3 用户阶段验收

阶段性检查导航和视觉方向即可，不替代最终用户真实使用测试。

### 5.3 阶段二：首页

#### 5.3.1 开发任务

1. 电影式 Hero 与决定性示意素材。
2. 证据条。
3. “寻访—采集—解码—传播”实践链。
4. 三路线章节。
5. 成果状态与结尾行动。

#### 5.3.2 自动化验证

- 首屏内容和动作可达性
- 320px、375px、768px、1024px、1440px 截图
- 减少动态效果快照
- 首屏布局稳定与图片尺寸检查

#### 5.3.3 退出条件

首页在一个首屏内清楚回答项目、实践方式和下一步动作；示意素材身份明确。

### 5.4 阶段三：路线与地点档案

#### 5.4.1 开发任务

1. `RouteIndex`、`RouteDiagram`、`SiteList` 和 `SiteDossier`。
2. 查询参数读取、校验、更新和浏览器历史恢复。
3. 上一地点、下一地点和复制链接。
4. 移动端地点优先的信息结构。
5. 坐标系、来源和内容状态展示。

#### 5.4.2 自动化验证

- 三路线与 13 地点数据遍历测试
- 有效和无效 URL 参数测试
- 前进、后退与复制链接测试
- 路线和地点键盘操作测试
- 移动端切换后的滚动与状态播报测试

#### 5.4.3 退出条件

用户能完成“选择路线—选择地点—阅读档案—继续下一地点”，且任何地点切换都不丢失上下文。

### 5.5 阶段四：成果与精神传承

#### 5.5.1 开发任务

1. 成果状态总览和 `OutcomeRecord`。
2. 数字展厅、档案、影片和报告的状态化展示。
3. 语义完整的图库与灯箱。
4. 人物原话、行动结果、影响时间线和最终行动。

#### 5.5.2 自动化验证

- 成果状态与动作一致性测试
- 灯箱 Esc、方向键、焦点捕获和焦点恢复
- 缺失素材和加载失败降级
- 键盘与 axe 扫描

#### 5.5.3 退出条件

用户不会把筹备中成果误认为已开放成果；传承页中的人物和影响内容均能追溯来源。

### 5.6 阶段五：素材替换系统

#### 5.6.1 开发任务

1. 建立图片转换和尺寸检查脚本。
2. 按固定素材 ID 生成 AVIF/WebP。
3. 验证占位素材与正式素材切换。
4. 补齐 alt、credit、captureDate 和授权状态。

#### 5.6.2 自动化验证

- 文件存在、格式、宽高比、尺寸和大小
- 不存在破损内部链接
- 非首屏媒体懒加载
- 正式素材切换不改变布局

#### 5.6.3 退出条件

替换单中的任一素材可在不修改组件结构的情况下完成晋级或回退。

### 5.7 阶段六：验证与发布

#### 5.7.1 自动化验证

必须完成：

1. TypeScript 类型检查；
2. ESLint；
3. Next.js 静态构建；
4. 数据完整性校验；
5. Playwright 四页面与主要交互测试；
6. axe-core WCAG 扫描；
7. 五个目标宽度视觉回归；
8. Lighthouse Performance、Accessibility 与 SEO；
9. 内部链接和素材路径检查。

#### 5.7.2 用户真实使用测试

自动化验证通过后，暂停发布并邀请设计方案规定的三类参与者完成真实任务：

1. 成果评审者在 60 秒内找到三条路线、一个地点档案和成果状态；
2. 移动端用户单手完成栏目、地点和图库流程；
3. 键盘用户不使用鼠标完成导航、路线、地点和灯箱操作。

#### 5.7.3 整体通过条件

只有自动化测试通过且三类真实用户测试反馈通过后，整体测试才可声明通过。真实使用测试未完成时，状态只能写为“实现和自动化测试已完成，等待用户验收”。

## 7. 风险与控制措施

### 7.1 内容真实性风险

#### 7.1.1 控制措施

集中来源记录、字段级来源、项目记录确认、状态门禁和构建校验。

### 7.2 坐标错误风险

#### 7.2.1 控制措施

正式地址先行、指定地理编码服务、坐标系固定、候选与正式数据分离、人工晋级。

### 7.3 地图合规与外部依赖风险

#### 7.3.1 控制措施

第一版不接入在线地图或行政边界；真实地图升级需要单独合规和基础设施决策。

### 7.4 素材延期风险

#### 7.4.1 控制措施

固定素材 ID、明确占位身份、尺寸稳定、状态驱动和逐项替换。

### 7.5 样式回归风险

#### 7.5.1 控制措施

按组件迁移、旧样式后删、五宽度截图、减少动态效果快照和阶段性审查。

### 7.6 静态部署风险

#### 7.6.1 控制措施

每阶段运行静态构建；不引入需要服务器的运行时功能；查询参数只承担客户端状态。

## 8. 开发启动门禁

### 8.1 已核定，可直接实施

#### 8.1.1 决策清单

- 保留 Next.js 静态导出和 GitHub Pages。

- 占位素材保持明确身份。

### 8.2 不阻塞基础开发，但阻塞正式内容晋级

#### 8.2.1 待项目方确认
