## 1. 实施目标与边界

### 1.1 实施目标

#### 1.1.1 目标状态

在保留 Next.js 静态导出、GitHub Pages 部署和 `/walking-coordinates` 基础路径的前提下，将现有展示原型重构为由集中数据、来源记录、内容状态和可替换素材驱动的生产级公开网站。

#### 1.1.2 核心结果

重构完成后，四个公开页面应当共同使用统一的设计 Token、导航、状态、路线、地点、成果和素材数据；用户能够在桌面端、移动端和键盘环境中完成设计方案规定的主要浏览流程。

#### 1.1.3 可信度要求

项目不得把 Agent 推断、搜索摘要、未确认坐标、示意影像或规划中的成果写成已核验事实。所有地点、历史说明、实践动作、坐标、媒体和成果状态都必须能够追溯到明确来源或项目团队确认记录。

### 1.2 本次重构范围

#### 1.2.1 页面范围

- 首页 `/`
- 寻访路线 `/journey`
- 数字成果 `/outcomes`
- 精神传承 `/legacy`

#### 1.2.2 工程范围

- 全局设计 Token、栅格、字体和交互状态
- 公共页头、移动菜单、页脚和页面元数据
- 路线、地点、来源、成果和素材的数据模型
- 首页叙事结构
- 路线索引、坐标关系图和地点档案
- 成果状态、图库灯箱和传承内容
- 静态图片交付、URL 状态恢复、无障碍和自动化验证

#### 1.2.3 非本轮范围

- 除高德安全代理外的后端业务服务、账号系统和内容管理后台
- 在线编辑和多人协作
- 导航、路径规划、实际轨迹推算或实时定位
- 未取得授权的第三方地图瓦片、摄影、视频或文字内容
- 将筹备中的成果包装成已完成成果

### 1.3 当前代码基线

#### 1.3.1 可保留部分

- Next.js App Router 与静态导出配置
- 四个一级路由
- 现有品牌红、深红、黑、白色彩基础

- `prefers-reduced-motion` 基础规则

#### 1.3.2 需要重构部分

- 页面内重复硬编码的路线、地点、成果与图库数据
- `globals.css` 与 `custom.css` 的重复覆盖关系

- 缺少焦点管理和键盘语义的地图节点与灯箱
- 未被页面引用的 `PracticeSite.tsx`
- 仅显示“现场照片 1—5”的无身份占位素材

## 2. 已核定的工程与数据决策

### 2.1 决策 D-001：接入高德真实在线地图

#### 2.1.1 核定结果

路线页使用高德地图 JS API 2.0 加载真实在线地图，以经过核验的 GCJ-02 坐标放置 13 个地点节点，并按同一路线的实践顺序连接节点。

路线连线表达寻访顺序，不表示实际步行、驾车、道路匹配或导航轨迹。地图不调用路径规划服务。

#### 2.1.2 核定理由

1. 项目方明确要求真实在线地图，并可以提供高德开放平台凭据。
2. 项目方拥有正在运行的 Nginx 服务，可通过 `/_AMapService` 转发高德 Web 服务请求并保护 `securityJsCode`。
3. 高德底图与 GCJ-02 坐标直接匹配，避免自行绘制行政边界或混合坐标系。
4. 顺序连线能够表达路线关系，同时避免把推算道路误认为团队真实轨迹。

#### 2.1.3 凭据与代理约束

- 地图渲染使用“Web 端（JS API）Key”。
- 地理编码使用单独的“Web 服务 Key”。
- `securityJsCode` 只保存在 Nginx 或服务器环境中，不进入仓库或前端构建产物。
- 前端通过 `serviceHost` 指向项目方 Nginx 的 `/_AMapService`。
- Key、域名和代理地址通过本地环境或部署参数传入。
- 项目根目录使用已被 `.gitignore` 忽略的 `Deploy.local.md` 保存实际服务器配置。
- 仓库提供不含真实域名和秘密的部署示例。

#### 2.1.4 失败隔离

高德脚本、代理或地图数据加载失败时，地图容器保持空白，不额外显示错误说明或替代地图。错误被限制在地图组件内部，不得影响路线索引、地点列表、地点档案、全站导航或其他页面。

### 2.2 决策 D-002：经纬度采用 GCJ-02 并保留来源

#### 2.2.1 核定结果

地点坐标的项目内标准为 GCJ-02。坐标使用判别联合类型表达缺失、候选和已核验三种状态，禁止使用 `0`、空字符串或虚构日期填充尚未核验的数据。

#### 2.2.2 数据结构

```ts
type CoordinateRecord =
  | {
      status: "missing";
    }
  | {
      status: "candidate";
      lat: number;
      lng: number;
      crs: "GCJ-02";
      target: "main-entrance" | "site-center";
      sourceId: SourceRecord["id"];
      queriedAt: string;
    }
  | {
      status: "verified";
      lat: number;
      lng: number;
      crs: "GCJ-02";
      target: "main-entrance" | "site-center";
      precision: "verified-poi" | "manual-pin";
      sourceId: SourceRecord["id"];
      verifiedAt: string;
      verifiedBy: "coordinate-reviewer" | "project-owner";
    };
```

#### 2.2.3 选择理由

- 高德地理编码直接返回高德经纬度，避免在项目中执行来源不明的坐标转换。
- GCJ-02 便于项目方在国内地图服务中人工复核。
- 明确坐标系可避免把 WGS84、GCJ-02 和 BD-09 数据混合使用。

#### 2.2.4 禁止事项

- 不根据建筑名称让 Agent 直接生成经纬度。
- 不复制搜索结果摘要中的坐标。
- 不将不同坐标系的数据直接放入同一数组。
- 不使用未注明入口、中心点或定位对象的“高精度”数字。
- 不在没有来源记录和角色审核时把坐标状态设为 `verified`。

### 2.3 决策 D-003：坐标采集采用候选生成与人工晋级流程

#### 2.3.1 输入

每个地点首先从场馆官网、北京市政府、北京市文物局或其他主管单位取得正式名称和结构化地址。

#### 2.3.2 候选生成

由项目方持有的高德 Web 服务 Key 调用地理编码接口。Key 只通过本地环境变量传入，不写入仓库。脚本输出候选文件，不直接修改正式地点数据。

建议命令：

```powershell
$env:WC_AMAP_WEB_KEY="<由项目方提供>"
npm run data:geocode
```

候选输出路径：

```text
data/generated/geocode-candidates.json
```

#### 2.3.3 人工复核

复核者必须同时检查：

1. 返回 POI 名称是否与正式地点一致；
2. 地址是否与主管单位页面一致；
3. 点位对应主入口还是场地中心；
4. 地点是否存在同名对象；
5. 坐标系是否为 GCJ-02。

#### 2.3.4 正式晋级

人工复核后，将坐标状态从 `candidate` 晋级为 `verified`，并填写 `verifiedAt` 与角色化 `verifiedBy`。自动脚本不得自行完成此步骤。

### 2.4 决策 D-004：事实内容使用来源分级制度

#### 2.4.1 来源等级

| 等级 | 来源 | 可承担用途 |
|---|---|---|
| A | 场馆官网、中央或地方政府、文物主管部门、项目团队原始记录 | 正式名称、地址、历史摘要、开放状态、实践事实 |
| B | 正式出版物、学术机构、权威数据库 | 历史补充、交叉验证 |
| C | 新闻报道、地图 POI、可信媒体 | 线索发现、地址或状态辅助核验 |
| D | 聚合页、社交媒体、搜索摘要、AI 输出 | 仅作搜索线索，不进入正式内容 |

#### 2.4.2 事实字段要求

- `name`：使用 `SourcedField<string>`，至少绑定一个 A 级来源。
- `officialAddress`：使用 `SourcedField<string>`，至少绑定一个 A 级来源。
- `historySummary`：拆为 `SourcedContentBlock[]`；每个事实块绑定来源，涉及具体年份、人物或事件时增加第二来源。
- `practiceSummary`：拆为 `SourcedContentBlock[]`，来源必须是项目团队原始记录。
- `coordinate`：坐标记录绑定指定地理编码来源，并在 `verified` 状态记录审核角色。
- 页面展示的来源从字段绑定关系派生，不使用无法校验的自由字符串。
- `reviewStatus` 与 `publicationStatus` 分别由审核角色和内容负责人确认。

#### 2.4.3 来源记录结构

```ts
interface SourcedField<T> {
  value: T;
  sourceIds: SourceRecord["id"][];
}

interface SourcedContentBlock {
  id: string;
  text: string;
  sourceIds: SourceRecord["id"][];
}

interface SourceRecord {
  id: string;
  title: string;
  publisher: string;
  url: string | null;
  recordRef: string | null;
  level: "A" | "B" | "C";
  sourceType:
    | "official-venue"
    | "government"
    | "project-record"
    | "publication"
    | "geocoder";
  accessedAt: string;
}
```

网页来源使用 `url`，项目内部确认使用不含个人信息的 `recordRef`。两者必须且只能存在一个，避免为团队原始记录伪造公开 URL。

#### 2.4.4 引用完整性门禁

构建前运行数据校验。任何 `ready` 或 `partial` 字段缺少规定来源时，构建失败；`placeholder` 或 `planned` 内容允许字段为缺失状态，但页面必须显示相应公开状态。校验器按字段读取 `sourceIds`，不接受来源记录中的模糊反向声明。

### 2.5 决策 D-005：十三处地点与实践日程已经项目方确认

#### 2.5.1 目标清单

实施以设计方案中的 13 个地点作为正式范围：

- 觉醒之路：5 处
- 烽火之路：5 处
- 进京之路：3 处

#### 2.5.2 已确认事实

项目方已经确认 13 个地点、三条路线归属、地点顺序、14 天实践周期和路线日期无误。这些项目事实以 `project-owner` 角色确认记录作为来源。

#### 2.5.3 仍需逐项核验的内容

### 2.6 决策 D-006：素材由清单驱动，不以文件是否存在推断状态

#### 2.6.1 核定结果

所有图片、视频、VR 和报告通过 `AssetRecord` 引用。页面只读取固定素材 ID，不直接拼接临时路径。

#### 2.6.2 占位素材

占位素材必须包含素材 ID、目标场景、宽高比、拍摄要求和“示意素材”标识。占位素材不得模拟真实历史照片，也不得使用无来源网络图片充当实践记录。

#### 2.6.3 正式素材晋级

正式素材只有在文件、授权、人物同意、alt、署名、拍摄日期和用途全部齐备时，才能切换为 `ready`。授权书和同意书原件保存在仓库外部，公开数据只保存状态和外部记录编号。

#### 2.6.4 素材状态结构

```ts
interface AssetBase {
  id: string;
  reviewStatus: ReviewStatus;
  publicationStatus: PublicationStatus;
  rightsStatus: "unknown" | "restricted" | "cleared";
  consentStatus: "not-required" | "pending" | "obtained";
  usageScopes: Array<"website" | "social" | "press" | "archive">;
  rightsRecordRef: string | null;
}

type AssetRecord =
  | (AssetBase & {
      assetStatus: "placeholder" | "planned";
      placeholderSrc: string;
    })
  | (AssetBase & {
      assetStatus: "ready";
      rightsStatus: "cleared";
      consentStatus: "not-required" | "obtained";
      finalSrc: string;
      alt: string;
      credit: string;
      captureDate: string;
    });
```

#### 2.6.5 图片交付

- 仓库保存预生成 AVIF 与 WebP。
- 组件使用 `<picture>`、明确宽高和响应式 `srcset`。
- 首屏主图按页面需要预加载。
- 非首屏媒体懒加载。
- 静态部署不依赖运行时图片转换服务。

### 2.7 决策 D-007：查询参数只保存交互状态

#### 2.7.1 URL 结构

```text
/journey?route=awakening&site=beida-honglou
```

#### 2.7.2 实现方式

- `/journey` 保持一个静态导出页面。
- 查询参数由客户端边界读取和更新。
- `useSearchParams` 所在组件放入 `Suspense` 边界，满足静态渲染要求。
- 参数必须与集中数据中的 slug 匹配。
- 无效参数回退到第一条路线和第一个地点，并使用 `replaceState` 修正 URL。
- 用户主动切换路线或地点时使用 `pushState`，保证浏览器前进和后退可恢复状态。

#### 2.7.3 SEO 规则

- 查询参数不产生独立静态页面或独立 canonical。
- `/journey` 是规范页面 URL。
- 分享链接保留参数以恢复交互状态。
- 如果未来需要每个地点独立被搜索引擎索引，再升级为静态动态路由 `/journey/[site]`，不在本轮提前实现。

### 2.8 决策 D-008：无障碍目标高于最低触控要求

#### 2.8.1 核定结果

WCAG 2.2 AA 是发布门槛；主要交互控件继续采用设计方案中的 44×44px 目标尺寸。44px 是项目设计目标，不误写成 WCAG 2.2 AA 的统一法定最小值。

#### 2.8.2 组件约束

- 路线和地点使用真实 `<button>` 或可访问的复合组件，不对纯 SVG `<g>` 直接绑定唯一交互。
- 路线图与地点列表提供等价操作路径。
- 灯箱使用原生 `<dialog>` 或经过验证的 portal 方案。
- 所有焦点状态使用至少 2px 的高对比轮廓。
- 移动菜单、灯箱和复合组件验证焦点进入、循环、退出与恢复。
- 减少动态效果模式不改变内容和操作能力。

### 2.10 决策 D-010：内部审核状态与公开状态分离

#### 2.10.1 状态结构

```ts
type ReviewStatus = "draft" | "needs-review" | "reviewed";

type PublicationStatus =
  | "placeholder"
  | "planned"
  | "partial"
  | "ready";
```

#### 2.10.2 使用规则

- `reviewStatus` 只回答数据是否经过人工审核。
- `publicationStatus` 只回答公开页面如何呈现内容。
- `reviewed` 不自动转换为 `ready`。
- `ready` 必须同时满足字段来源、素材授权和真实访问动作要求。
- 审核身份使用 `project-owner`、`coordinate-reviewer`、`rights-reviewer` 等角色标识。
- 公开仓库不保存审核人姓名、授权书原件或内部联系方式。

### 2.11 决策 D-011：成果使用完整状态模型

#### 2.11.1 数据结构

```ts
interface OutcomeBase {
  id: string;
  order: number;
  title: SourcedField<string>;
  description: SourcedContentBlock[];
  ownerRole: string;
  reviewStatus: ReviewStatus;
  publicationStatus: PublicationStatus;
  assetId: string | null;
  updatedAt: string;
}

type OutcomeRecord =
  | (OutcomeBase & {
      completionStatus: "planned" | "in-progress";
      deliveryCondition: string;
      access: null;
      publishedAt: null;
    })
  | (OutcomeBase & {
      completionStatus: "complete";
      deliveryCondition: null;
      access: {
        kind: "link" | "download" | "play";
        href: string;
        label: string;
      };
      publishedAt: string;
    });
```

#### 2.11.2 校验规则

- 未完成成果必须具有交付条件，不能具有公开访问动作。
- 完成成果必须具有真实访问地址、动作文案、发布日期和来源。
- 页面按钮只从 `access` 派生，不根据标题或完成百分比自行生成。

### 2.12 决策 D-012：部署秘密与服务器配置不进入仓库

#### 2.12.1 文件规则

- `.env.local` 保存本地 JS API Key、Web 服务 Key 和代理地址，并由现有 `.gitignore` 忽略。
- `Deploy.local.md` 保存实际 Nginx 域名、配置文件位置、验证命令和回退步骤，并由 `.gitignore` 忽略。
- `Deploy.example.md` 提供可提交的占位配置和部署流程，不包含真实域名、IP、Key 或 `securityJsCode`。
- 正式部署阶段必须向项目方交付完整 Nginx 增量配置和验证步骤。

#### 2.12.2 Nginx 目标接口

前端配置：

```ts
window._AMapSecurityConfig = {
  serviceHost: "https://<代理域名>/_AMapService",
};
```

Nginx 为 `/_AMapService/` 请求追加服务器端 `securityJsCode`，再转发到高德 Web 服务。实际配置只写入 `Deploy.local.md` 和服务器，不写入仓库。

## 3. 数据搜寻与核验工作流

### 3.1 地点事实工作流

#### 3.1.1 建立待核验表

为 13 个地点创建记录，初始状态均为 `draft`，字段包含正式名称、设计名称、路线、顺序、正式地址、坐标、历史摘要、实践摘要和来源。

#### 3.1.2 正式名称核验

优先查询场馆官网、北京市文化和旅游局、北京市文物局或北京市政府页面。记录页面标题、发布机构、URL 和访问日期。

#### 3.1.3 地址与坐标核验

先确定正式地址，再执行第 2.3 节的地理编码候选与人工晋级流程。坐标不能反向决定正式地点身份。

#### 3.1.4 历史摘要核验

摘要先写“事实句清单”，每句绑定来源 ID，再组合成页面段落。无法找到来源的句子保持缺失，不由 Agent 补写。

#### 3.1.5 实践记录核验

实践动作、拍摄日期、采访对象和采集方式只能来自团队日志、照片 EXIF、采访记录或负责人确认。

#### 3.1.6 内容负责人确认

负责人逐地点确认后，将 `reviewStatus` 从 `draft` 升级为 `reviewed`；只有 `reviewed` 数据才能将 `publicationStatus` 升级为 `partial` 或 `ready`。

### 3.2 成果状态工作流

#### 3.2.1 成果登记

每项成果记录负责人、实际文件或访问地址、当前完成度、公开权限、发布日期和更新日期。

#### 3.2.2 状态判定

- `planned`：尚无可验证交付物。
- `partial`：存在可验证的阶段性内容，但未达到完整公开标准。
- `ready`：用户点击后可以访问与文案一致的正式内容。

#### 3.2.3 动作一致性

没有真实目标时不显示“进入”“播放”“下载”等动作。筹备中内容只显示状态和交付条件。

### 3.3 素材工作流

#### 3.3.1 入库

素材按设计方案规定的 ID 和目标路径入库，保留原始文件、网页交付文件和授权记录之间的对应关系。

#### 3.3.2 自动检查

脚本检查文件是否存在、尺寸、宽高比、格式、文件大小、必填 alt 和 credit。

#### 3.3.3 人工检查

人工确认画面身份、人物授权、叙事用途、裁切安全区和颜色处理。

#### 3.3.4 发布晋级

自动与人工检查均通过后，将 `assetStatus` 更新为 `ready`，并分别更新审核与公开状态。页面不得根据 `finalSrc` 非空自动推断为 `ready`。

### 3.4 Agent 工作约束

#### 3.4.1 允许

- 从指定来源提取候选事实并保留原始 URL；
- 生成待核验表、校验脚本和缺失项报告；
- 根据已确认数据编写组件与测试；
- 标记来源冲突和无法确认的内容。

#### 3.4.2 不允许

- 以模型记忆补齐地点地址、坐标、历史年份或项目实践事实；
- 用搜索摘要代替原始来源；
- 在来源冲突时自行选取更符合叙事的版本；
- 将文件存在、页面美观或字段非空推断为内容已完成；
- 生成看似真实的历史现场照片作为正式证据。

#### 3.4.3 冲突处理

来源冲突时保留全部候选、记录差异并标记 `needs-review`。在项目负责人确认前，页面使用中性文案或保持字段缺失。

## 4. 目标工程结构

### 4.1 页面与组件

#### 4.1.1 页面层

页面负责元数据、章节顺序和服务端静态结构，不持有重复业务数据。

#### 4.1.2 交互层

客户端组件只用于移动菜单、路线与地点选择、URL 同步和灯箱。

#### 4.1.3 组件建议

```text
components/
  shell/
    SiteHeader.tsx
    MobileMenu.tsx
    SiteFooter.tsx
  evidence/
    EvidenceStrip.tsx
    StatusBadge.tsx
    SourceList.tsx
  media/
    ResponsiveMedia.tsx
    MediaPlaceholder.tsx
    MediaDialog.tsx
  routes/
    RouteIndex.tsx
    AMapRouteMap.tsx
    SiteList.tsx
    SiteDossier.tsx
  outcomes/
    OutcomeRecord.tsx
```

### 4.2 样式系统

#### 4.2.1 文件边界

- `app/globals.css`：重置、Token、基础排版、焦点和减少动态效果。
- `styles/layout.css`：全局容器、栅格和响应式结构。
- `styles/components/*.css`：组件样式。
- 页面局部样式使用 CSS Module 或明确页面命名空间。

#### 4.2.2 迁移规则

新组件完成后再删除对应旧选择器。不得先整体删除现有样式，也不得继续依赖 `!important` 叠加覆盖。

#### 4.2.3 Token 规则

颜色、内容宽度、间距、动效、圆角、层级和焦点统一通过 Token 使用。页面组件不得重复声明同义魔法值。

### 4.3 内容校验

#### 4.3.1 类型校验

TypeScript 使用 `satisfies` 保证数据形状，并由纯函数验证跨记录约束。

#### 4.3.2 跨记录约束

- 路线引用的地点必须存在且属于该路线。
- 地点顺序在路线内唯一。
- 素材 ID 全局唯一。
- `ready` 素材文件必须存在。
- `ready` 内容必须拥有规定来源。
- slug 必须稳定、唯一且可安全进入 URL。

“内容发布就绪”要求真实地点记录、真实素材与授权、成果链接、人物原话、坐标人工核验和三类用户真实使用测试全部通过。只有该状态可以声明整体完成。

## 7. 风险与控制措施

### 7.1 内容真实性风险

#### 7.1.1 控制措施

集中来源记录、字段级来源、项目记录确认、状态门禁和构建校验。

### 7.2 坐标错误风险

#### 7.2.1 控制措施

正式地址先行、指定地理编码服务、坐标系固定、候选与正式数据分离、人工晋级。

### 7.3 地图合规与外部依赖风险

#### 7.3.1 控制措施

使用高德官方在线底图和 GCJ-02 坐标；通过 Nginx 安全代理保护 `securityJsCode`；只连接核验地点顺序，不生成未经确认的导航轨迹；地图失败时保持空白并与其他服务隔离。

### 7.4 素材延期风险

#### 7.4.1 控制措施

固定素材 ID、明确占位身份、尺寸稳定、状态驱动和逐项替换。

### 7.5 样式回归风险

#### 7.5.1 控制措施

按组件迁移、旧样式后删、五宽度截图、减少动态效果快照和阶段性审查。

### 7.6 静态部署风险

#### 7.6.1 控制措施

每阶段运行静态构建；前端仍为纯静态站点；Nginx 只承担高德安全代理；查询参数只承担客户端状态；代理部署和回退记录在被忽略的本地部署文件中。
